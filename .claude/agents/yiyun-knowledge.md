### For Frontend Engineer Roles

**Q: You shipped 65 PRs in 8 months. How do you maintain quality?**
A: Code review (submitter *and* reviewer), TypeScript strict mode catches 80% of bugs, and I scope PRs to ship only what's needed (not cleanup). Regression catching: every PR that touches state gets manual testing on real RTC state machines.

**Q: Tell me about your approach to state management.**
A: MobX reactive patterns — define computed state, trigger side effects via reactions, keep actions explicit. Learned this under pressure (real-time classroom, concurrent WebSocket events). The key: clear ownership of which layer owns which state (RTC SDK vs. app vs. UI).

**Q: What's a time you had to push back on scope?**
A: Implement permission-state model for screen-share. First instinct: add a new state layer. Reality check: ChatProvider and participant-panel boundaries were messy; anything new would rot. Scoped first refactor, *then* permission model. Took longer upfront; shipped cleaner, teammates thanked me later.

### For Design Engineer Roles

**Q: How do you bridge design and engineering?**
A: Speak both languages fluently. With designers: I read Figma, ask "why this interaction" not "why not this color." With engineers: I'm comfortable with component boundaries, state tradeoffs, and technical constraints. I can translate "make this more discoverable" → "increase tap target, improve affordance contrast, reduce menu depth" → concrete code.

**Q: What's your approach to design systems?**
A: Tokens first. Define spacing scale, color scale, typography scale. Then components (Button → Input → Form). Lock down behavior in Storybook/tests. Only then ship variants. At AmazingTalker, we built a scalable design system that worked across web + Electron + Ant Design without diverging.

**Q: Real example: design/code conflict you've resolved?**
A: Classroom UI: designer wanted smooth animations on participant list updates. Reality: list can be 50+ items, smooth animations would tank performance. Solution: animation only for *entering* participants (common case), instant update for *leaving* (rare + already disruptive). Shipped fast, looked great, performed well.

### For PM / TPM Roles

**Q: Walk me through a time you owned a product decision end-to-end.**
A: Checkout redesign at AmazingTalker. Started with data: drop-off spike on cart-review step. Hypothesis: too many form fields. Solution design: progressive disclosure, inline validation, save draft. Implementation: three PRs (form component, session storage, visual polish). A/B test: +14% conversion. Shipped in 2 sprints.

**Q: How do you talk to engineers about scope?**
A: Decompose upfront. "Full redesign" isn't a spec; "Step 1: refactor component boundaries (unblocks other work)" is. I identify technical prerequisites *before* asking them to build, so I'm not blindsiding them. And I stay hands-on enough to understand feasibility — if I'm wrong about complexity, they can push back with data.

**Q: Tell me about a time you killed a feature idea.**
A: Track Stock project: originally planned RAG-based research assistant. Started building. Realized: knowledge base needs constant curation to stay accurate, and I didn't have time. Killed it. Shipped multi-factor scoring instead (same time budget, clearer ROI). Users can read the news links directly; AI doesn't need to synthesize here.

**Q: How do you measure success?**
A: Metrics + qualitative. Checkout redesign: +14% conversion (metric). Classroom UI: user feedback from teachers + support tickets drop (qualitative). Side projects: Ship fast, iterate based on usage. Not every feature needs metrics; some are "if users ask for it once, we've validated enough."

**Q: What's your relationship with technical debt?**
A: Real debt, not just "old code." Example: ChatProvider mess at AmazingTalker — that was actual debt blocking the permission model. Repaying it unblocked velocity. But "this code is ugly" without an impact isn't debt; it's a hygiene preference. I ship fast first, refactor when it's blocking next ship.
